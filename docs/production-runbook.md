# Second Date production runbook\n\n## Deployment order\n\n1. Provision PostgreSQL.\n2. Set production environment variables.\n3. Apply the database schema.\n4. Deploy the Next.js application.\n5. Verify /api/health.\n6. Verify /api/readiness.\n7. Register and verify the Stripe webhook.\n8. Verify the billing portal.\n9. Verify the reminder cron with a test Plus account.\n10. Run the production smoke test.\n11. Start the 50-user validation cohort.\n\n## Required production variables\n\n- DATABASE_URL\n- APP_URL\n\nThe application can serve the core product when those are present.\n\n## Billing variables\n\n- STRIPE_SECRET_KEY\n- STRIPE_WEBHOOK_SECRET\n\nBoth are required before billing is considered configured.\n\n## Reminder variables\n\n- RESEND_API_KEY\n- REMINDER_FROM_EMAIL\n- CRON_SECRET\n\nAll three are required before reminders are considered configured.\n\n## Database setup\n\nApply the current Drizzle schema with:\n\n    npm run db:push\n\nRun this deliberately against the intended environment. DATABASE_URL determines the target.\n\n## Readiness checks\n\n/api/health checks database connectivity only.\n\n/api/readiness reports four booleans without exposing secret values: database, appUrl, billing, reminders. HTTP 200 means the core hosted application is ready. Billing/reminders may still be false until those optional systems are enabled. HTTP 503 means the core hosted application is not ready.\n\n## Production smoke test\n\nRun:\n\n    SECOND_DATE_URL=https://your-production-host npm run smoke:production\n\nThe script checks the marketing page, app, legal pages, health, and readiness endpoints.\n\n## Stripe verification\n\nUse Stripe test mode first. Verify yearly checkout, monthly checkout, checkout return verification, webhook-created Plus entitlement, billing portal access, cancellation downgrade, and account deletion with an active subscription.\n\n## Reminder verification\n\nCreate a test Plus account, enable reminders, and create an item whose reminder date is today. Call the cron endpoint with the configured bearer secret and verify exactly one email is delivered, a second call does not duplicate the digest, a failed delivery can retry, and reminder analytics records only successful delivery.\n\n## Rollback\n\nIf a deployment introduces a runtime regression, roll back the deployment artifact, confirm health/readiness, inspect runtime errors, and preserve failed webhook/reminder evidence before retrying. Do not roll back the database blindly after user writes have occurred. Prefer forward-compatible schema fixes.\n
